# Cursor Spider Coach — Reflection

## What did I build?

I built **Cursor Spider Coach**: a desktop coding companion for beginners who learn by prompting in Cursor, not by reading stack traces. A small spider sits on the screen with a coaching line that changes when the user is drafting in Composer, waiting on the agent, stuck in a long pause, or finishing a good run. Eight coaching states map those moments to encouragement and practical nudges (sharper prompts, patience, unstuck strategies, small wins). The tool runs locally on the user’s machine: a spider overlay, a Cursor extension that notices Composer activity, and a shared coaching brain that picks what to say. It is meant to feel like a mascot with opinions showing up in the workflow when a new coder might otherwise feel lost or alone.

## What decisions did I make?

Once on Cursor, I chose a **three-part stack**—React overlay + Electron host + Cursor extension—instead of a hosted web app or extension-only UI. Cursor cannot draw a frameless always-on-top pet inside the IDE, and a public URL would not reach the user’s Composer session; local Electron plus a localhost bridge keeps the spider on the glass while the extension reads real editor signals. For **data**, I narrowed scope to “vibe-only” triggers (Composer typing, agent work, quiet time, terminal only when the agent was recently active) and removed early ideas like broad file-edit or terminal-success sensors that fired too often and felt like linting, not coaching. In **MP2a** I proposed a desktop companion inspired by Claude’s mascot and planned to build it in **Bolt**. I later realized that was likely not technically workable for what I wanted: **Claude Code runs in the terminal**, and a Bolt-hosted web app has no native way to read session state or terminal output unless something else sits in the middle—a local server, webhooks, or files the CLI writes while the app polls. I could not see a clean path to “the pet knows what Claude Code is doing” without that bridge, so I **pivoted to Cursor Spider Coach** and used **Cursor itself** to help me build it.

## What would I do differently?

I would **define the user and product position before designing triggers**. At first I treated the audience loosely as **people who are new to Cursor**, which sounded simple but lumped together two very different groups: **people with an engineering background who still code in the editor**, and **vibe coders with little or no coding background** who mostly live in Composer. I started with terminal-based triggers: runs finishing, command output, saves, because they were easy to detect. Once I lived with them, they **did not add much value**: the spider mostly **re-announced status** the user could already see (“the terminal finished,” “something ran”) rather than coaching the next move. Even for people with an engineering background, those lines felt like **noise, not guidance**, too generic to change how someone works. That failure forced me to **relook at who this was really for**. I narrowed the audience to **vibe coders**, people learning through Composer and prompts, not through watching the terminal, and rebuilt triggers around those moments (drafting, agent work, long silence, small wins). I would run that persona exercise **first**, so I did not spend time on sensors that could never produce useful coaching. I would also **write positioning copy early** (who it is *not* for, what “coaching” means here) so every feature could be judged against one sentence instead of drifting.

## What does this work demonstrate?

This work demonstrates **critical evaluation and judgment**, not a claim that I hand-wrote the codebase. I decided what the product should *not* do (terminal spam, generic AI chat in the bubble) and where **human taste** must stay in control. The **guidance library** is fully authored: fixed pools of lines I shaped for voice and safety, with **random selection** so the spider does not repeat the same sentence and feel robotic—because I did not want open-ended AI replies that might hallucinate and break trust in a beginner’s moment of confusion. I used AI heavily to implement, debug, and iterate, while I owned **product thinking**: eight states, trigger table, message tone, when to interrupt vs. wait, and README clarity for people with no class context. The result is an example of **human-centered design with algorithmic backing**—warmth and judgment on the surface, rules and data underneath—and of collaborating with AI on what each side does best.
